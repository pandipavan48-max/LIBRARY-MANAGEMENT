Abstract

The rapid growth of digital information and the increasing volume of books, journals, and academic resources in modern libraries demand a robust, scalable, and intelligent management system. Traditional relational database systems, while powerful, often fall short when handling semi-structured data, graph relationships, and real-time recommendations at scale. This project addresses these challenges by designing and implementing a Library Management and Book Recommendation System using two complementary NoSQL database technologies: MongoDB and Neo4j.

MongoDB, a document-oriented NoSQL database, is used to store and manage core library entities — Books, Members, and Transactions — in a flexible JSON-like format. Its schema-less design allows seamless storage of heterogeneous book records, while its rich aggregation pipeline enables complex analytical queries such as genre distribution, most-borrowed books, and overdue fine calculations.

Neo4j, a property graph database, models the social and relational aspects of the library ecosystem. Members and Books are represented as graph nodes, and borrowing activities create edges between them. This graph structure enables powerful Collaborative Filtering — a recommendation technique that identifies members with similar reading histories and suggests books they have not yet read, all expressed through concise and expressive Cypher queries.

The system provides a complete web-based interface built with HTML5, CSS3, and vanilla JavaScript, featuring an Admin Dashboard, Books Management (CRUD), Member Registration, Transaction Tracking (Issue/Return), Fine Calculation, and an interactive Graph Recommendation engine. The project demonstrates how combining two NoSQL paradigms — document store and graph database — produces a system that is more capable and natural than either database alone.

The outcome is a fully functional, visually rich library portal that demonstrates practical application of NoSQL concepts including document modeling, graph traversal, Cypher query language, aggregation pipelines, and CRUD operations — fulfilling all the requirements of the NoSQL Problem-Based Learning assignment.

Chapter 1 — Introduction

1.1 Background

Libraries are the cornerstone of academic institutions, providing students and faculty with access to a wealth of books, journals, and learning resources. As the volume of library resources grows, managing them efficiently becomes increasingly critical. Traditional Library Management Systems (LMS) built on Relational Database Management Systems (RDBMS) suffer from rigid schemas, poor scalability for large datasets, and inability to natively model complex relationships such as "members who read similar books."

The emergence of NoSQL databases has opened new possibilities for building flexible, high-performance, and intelligent data-driven applications. NoSQL databases support a variety of data models — documents, graphs, key-value stores, and wide-column stores — each suited to different problem domains. This project exploits this diversity by combining two NoSQL paradigms for a single real-world application.

1.2 Project Overview

LibraryOS is a web-based Library Management and Book Recommendation System that uses:

  • MongoDB — to store structured library records (books, members, transactions) in a flexible document format with powerful querying.
  • Neo4j — to model the borrowing relationship graph and generate personalized book recommendations using graph traversal and Cypher queries.

The system provides a complete, modern web interface covering all aspects of library operations — from book cataloguing and member management to transaction tracking, fine computation, and AI-inspired recommendations.

  5. Build a fully functional, user-friendly web interface for library management.

Chapter 2 — Problem Statement

2.1 Limitations of Traditional Systems

Existing library management systems, predominantly built on relational databases like MySQL or Oracle, face several significant challenges in the modern digital era:

  • Rigid Schema: Books come in many forms — textbooks, journals, e-books, research papers — each with different attributes. RDBMS requires a predefined schema, making it difficult to store heterogeneous book data.
  • Scalability Issues: As library collections grow to millions of records, RDBMS struggles with horizontal scaling and distributed data management.
  • No Native Relationship Modeling: Recommendation systems require traversing complex relationships (who borrowed what, which books are similar). SQL JOINs across large datasets are slow and cumbersome.
  • Lack of Recommendation Engine: Most existing systems do not provide intelligent book recommendations — a feature increasingly expected by users.
  • Poor Performance on Graph Queries: Finding "books commonly borrowed together" requires multi-level JOINs in SQL, but is a simple 2-hop graph traversal in Neo4j.

2.2 Proposed Solution

This project proposes a NoSQL-based solution that addresses all the above limitations:

ProblemSolutionDatabase
Rigid schema for diverse booksDocument model with flexible JSON schemaMongoDB
Scalability bottleneckHorizontal sharding and replica setsMongoDB
Complex JOIN queriesEmbedded documents and referencesMongoDB
No recommendation engineGraph traversal + Collaborative FilteringNeo4j
Slow relationship queriesNative graph model with Cypher queriesNeo4j

2.3 Scope of the Project

The scope of this project includes the complete lifecycle of library management: book cataloguing, member registration, book issuance and return, overdue fine management, analytics and reporting, and a Neo4j-powered recommendation system. The frontend is built as a web application accessible via any modern browser without requiring additional software installation.

3.1 Overall Architecture

LibraryOS follows a three-tier architecture consisting of a Presentation Layer (web frontend), Application Logic Layer (JavaScript), and a Data Layer (MongoDB + Neo4j). The system is designed to be lightweight and deployable without a traditional backend server.

3.2 Data Flow Diagram

The following describes the data flow for the two main workflows:

Book Issuance Flow (MongoDB)

  1. Admin selects member and book from the Issue Book form.
  2. System validates member status (Active/Suspended) and book availability.
  3. A new Transaction document is inserted into MongoDB's transactions collection.
  4. The book's available count is decremented in the books collection.
  5. A Neo4j BORROWED relationship is created between the Member and Book nodes.

Recommendation Flow (Neo4j)

  1. Admin selects a member in the Recommendations page.
  2. A Cypher query traverses the graph: Member → borrowed → Books → borrowed by others → other Books.
  3. Books not yet borrowed by the target member are ranked by recommendation score.
  4. Top 5–6 recommendations are displayed with score and reason.

Chapter 5 — Database Design: Neo4j (Graph Model)

5.1 Property Graph Model

Neo4j is a native graph database that stores data as nodes (entities) and relationships (edges), each with associated properties. This model naturally represents the borrowing ecosystem of a library, where Members borrow Books, Books belong to genres, and Members with similar interests can be connected.

Chapter 6 — Why NoSQL? Database Justification

6.1 Why MongoDB for Library Records?

MongoDB was selected for the core library records because:

  • Flexible Document Model: Different book types (textbooks, journals, e-books) have different attributes. MongoDB's schema-less design accommodates this variation naturally.
  • Rich Query Language: MongoDB's query language supports filtering, sorting, projection, and aggregation — ideal for complex library analytics.
  • Horizontal Scalability: MongoDB's sharding allows the library database to scale across multiple servers as collections grow.
  • Native JSON Storage: Modern web applications communicate via JSON; MongoDB stores data natively in BSON, reducing serialization overhead.
  • Aggregation Pipeline: MongoDB's aggregation pipeline enables powerful analytics queries (e.g., most borrowed books by genre) without complex SQL.

6.2 Why Neo4j for Recommendations?

  • Native Graph Model: Borrowing patterns naturally form a bipartite graph (Members ↔ Books). Neo4j's property graph model is a direct fit.
  • Cypher Query Language: Cypher's pattern-matching syntax makes graph traversal queries readable and expressive.
  • Efficient Relationship Traversal: Neo4j traverses relationships in O(log n) time using index-free adjacency — far faster than SQL JOINs for graph queries.
  • Built-in Graph Algorithms: Neo4j provides algorithms (PageRank, Louvain, Jaccard Similarity) for advanced recommendation scoring.

8.1 MongoDB CRUD Operations

CREATE — Insert a new book

db.books.insertOne({ title: "Atomic Habits", author: "James Clear", genre: "Self-Help", isbn: "978-0-73-521129-2", copies: 8, available: 6, rating: 4.9, borrowed: 0, shelf: "E-1" });

READ — Find available books by genre

db.books.find( { genre: "Technology", available: { $gt: 0 } } ).sort({ rating: -1 }).limit(10);

UPDATE — Issue a book (decrement available)

db.books.updateOne( { _id: ObjectId("...") }, { $inc: { available: -1 }, $inc: { borrowed: 1 } } );

DELETE — Remove a book

db.books.deleteOne({ _id: ObjectId("...") });

8.2 MongoDB Aggregation Queries

Top borrowed books by genre
db.books.aggregate([ { $group: { _id: "$genre", total: { $sum: "$borrowed" } } }, { $sort: { total: -1 } } ]);
Calculate total outstanding fines
db.transactions.aggregate([ { $match: { status: "Overdue" } }, { $addFields: { daysOverdue: { $dateDiff: { startDate: "$dueDate", endDate: "$$NOW", unit: "day" }}, }}, { $addFields: { fine: { $multiply: ["$daysOverdue", 5] } } }, { $group: { _id: null, totalFine: { $sum: "$fine" } } } ]);

Chapter 9 — Book Recommendation System

9.1 Collaborative Filtering Algorithm

Collaborative Filtering (CF) is a recommendation technique that makes predictions about a user's interests by collecting preferences from many users. The key assumption is: "If Person A and Person B both borrowed Books X and Y, and Person B also borrowed Book Z, then Book Z is likely a good recommendation for Person A."

In LibraryOS, this is implemented naturally through the Neo4j graph: Members who share borrowed books are implicitly connected via the graph structure. A Cypher query traverses two hops from the target member to discover recommended books.

9.2 Core Recommendation Cypher Query

// Collaborative Filtering — 2-hop graph traversal MATCH (u:Member {id: $memberId})-[:BORROWED]->(b:Book) <-[:BORROWED]-(similar:Member)-[:BORROWED]->(rec:Book) WHERE NOT (u)-[:BORROWED]->(rec) RETURN rec.title, rec.author, rec.genre, COUNT(*) AS recommendationScore, COLLECT(DISTINCT similar.name) AS recommendedBy ORDER BY recommendationScore DESC LIMIT 5;

9.3 Genre-Boosted Recommendation Query

// Genre-aware recommendation MATCH (u:Member {id: $memberId})-[:BORROWED]->(b:Book) WITH u, COLLECT(DISTINCT b.genre) AS preferredGenres MATCH (rec:Book) WHERE rec.genre IN preferredGenres AND NOT (u)-[:BORROWED]->(rec) RETURN rec.title, rec.genre, rec.rating, rec.rating * 10 AS genreScore ORDER BY genreScore DESC LIMIT 5;

9.4 Recommendation Scoring Formula

The final recommendation score combines multiple signals:

RecommendationScore = (GenreMatch × 40) + (BookRating × 8) + (BorrowCount × 1, capped at 30) + (RandomSalt × 10) // for diversity

Chapter 12 — Conclusion and Future Work

12.1 Conclusion

This project successfully demonstrates the design and implementation of a real-world Library Management and Book Recommendation System using two complementary NoSQL databases: MongoDB and Neo4j.

MongoDB proved ideal for storing structured-yet-flexible library records, supporting rich CRUD operations, complex aggregations, and scalable document management. Neo4j's property graph model elegantly captured the borrowing relationships between members and books, enabling a collaborative filtering recommendation engine that would be cumbersome to implement with traditional SQL.

The combination of both databases demonstrates a key principle of modern database design: "Use the right tool for the right job." Document databases excel at managing entity records; graph databases excel at managing relationships. Together, they produce a system more powerful and more natural than either alone.

All objectives of the NoSQL PBL assignment were met — CRUD operations were demonstrated on both databases, the advantages of NoSQL over RDBMS were clearly justified, and a complete working application with a polished user interface was delivered.

12.2 Future Enhancements

  • Mobile App: React Native app for members to browse books and check availability.
